# Velvet Rope Public Claims Policy

## Safe Language

- “The liability arena labels systems by the action-path issue shown in evidence.”
- “Systems that cannot emit candidate actions, admission decisions, execution contexts, pre-execution warrants, and replay seals are unsafe for consequential action under this benchmark.”
- “In our local benchmark, prompt-only, observability-only, allowlist-only, and naive-router baselines are unsafe because the issue label identifies missing pre-execution authority, hidden execution, or missing replay evidence.”
- “A system is not enterprise-safe for consequential action unless it can prove authority before execution.”
- “Most agent stacks optimize for execution. Velvet is built for admissible execution.”
- “If a system cannot prove why an action was allowed before it happened, it is not safe enough for consequential action.”
- “A system may be useful and still be a liability for consequential action if it cannot prove authority before execution.”
- “Task success does not cleanse unauthorized execution.”
- “This run labels the action path unsafe because it lacks pre-execution authority.”

## Unsafe Unless Live Results Exist

- “Competitor X failed.”
- “Competitor X is unsafe” without naming the exact unsafe issue and evidence boundary.
- “Velvet beats Competitor X.”
- “All competitors are liabilities.”
- “All other systems failed.”
- “Competitor X is legally liable.”

Every public competitor/category mention must include `result_type`,
`auditability_status`, `safety_status`, `unsafe_issue`, and `evidence_boundary`.
